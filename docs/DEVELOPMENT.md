本文是项目设计文档，修改设计前需先更新本文。项目推进过程中的决策与问题记录在 [devlog.md](devlog.md)，文中公式的推导见 [DERIVATIONS.md](DERIVATIONS.md)。

## 1. 背景信息

### 1.1 目标与背景

项目名称为 `steamsales-estimator`。项目目标是用公开数据估算单款 Steam 游戏的销量（免费游戏只给玩家数，不换算成销量），输出估计值、95% 区间、置信标签和可复查的计算过程。

本项目的方法参考 Gamalytic（第三方销量估算网站）公开的三篇文章。销量估算基于销量等于评测数乘以倍数 $k$ 的基本关系：

$$
S = R \cdot k
$$

其中 $S$ 为目标真值（近年真值表里是销量，2018 年训练集里是玩家数），$R$ 为评测数，$k$ 为单条评测对应的销量倍数。倍数 $k$ 因游戏而异，受价格、年代、类型、好评率、折扣习惯等因素影响。项目的工作流程依次为：采集数据、估计 $k$、检验可信度、展示结果。

基于评测数的预测称为信号 A（评测数乘倍数 $k$）。为使估计更准，另用同时在线人数估算销量，称为信号 B（由在线人数累计总游玩小时，再除以人均游玩小时）。两路估计在对数空间按各自的整体误差加权融合。

**方法依据**

| 文章 | 本项目采用的内容 |
| --- | --- |
| [A new way to estimate steam game sales](https://gamalytic.com/blog/a-new-way-to-estimate-steam-games-sales)（2023-01-20） | 信号 B 的思路：由同时在线人数累计总游玩小时，再除以人均游玩时长得到玩家数。 |
| [What makes people review your game? A deep dive into the Steam's sales/review ratio](https://gamalytic.com/blog/a-deep-dive-into-the-steam-review-ratio)（2023-07-23） | 信号 A 的特征选取：发售时间（含 2019 年 Steam 提示写评测后倍数减半）、价格与折扣、好评率、评测者游玩时长、类型标签、评测数量。 |
| [How to accurately estimate Steam game sales](https://gamalytic.com/blog/how-to-accurately-estimate-steam-sales)（2023-05-13） | 多种估计加权合并的思路；用 2018 年泄露数据集校正老游戏；以“误差 10%/30%/50%/70% 以内的比例”评价；评测数乘固定倍数的基线；有公开销量的对照表（校准/测试集来源之一）。 |

本项目没有采用的内容：畅销榜排名法、抽样公开玩家资料法、收入估计。与 Gamalytic 做法的具体差别（如在线人数取月均值而非逐小时、时长取评测者中位数并经拟合换算）见“方法”一章。

### 1.2 术语

样本，定义为一款游戏加一个截止日。截止日是样本全部输入数据截止的日期，一切输入只取截止日之前的数据。训练集的截止日为 2018-07-01；校准/测试集的截止日为销量公布日，或按“首日/首周/首月”换算的日期。

训练集（`train`）采用 2018-07-01 Ars Technica 公开的玩家数表，加上截至该日的评测数据，其真值是玩家数，非销量。校准/测试集（`calib`）采用已人工核对好的近年销量真值表，作为现成输入导入，每款游戏只保留一条最准的记录，真值是确切销量；同一批数据既用于校准，也用于留一法测试。不另设封存集：真值只有一百多条，再留出一部分会让校准不稳、测出的命中率误差太大；改用留一法，凡是从这批数据算出来的数，预测某款游戏时都不用到它自己。

评测数指截止日前所有语言的评测总数，包括非 Steam 内购买的评测；Steam 内购买占比作为单独特征输入模型。倍数 $k$ 定义为真值除以评测数，即 $k = S / R$。

单条样本预测命中的定义为相对误差不超过 30%：

$$
\left| \frac{\hat{S}}{S} - 1 \right| \le 0.3
$$

其中 $\hat{S}$ 为销量估计值。该条件在对数空间的形式见 [DERIVATIONS.md](DERIVATIONS.md)“命中条件”一节。

销量估计的预测区间定义为对数空间下的对称区间，名义覆盖率为 95%：

$$
\left[\, \hat{S}\, e^{-1.96\sigma},\ \hat{S}\, e^{1.96\sigma} \,\right]
$$

其中 $\sigma$ 为对数销量估计值 $\ln \hat{S}$ 的标准差。推导和成立条件见 [DERIVATIONS.md](DERIVATIONS.md)“预测区间”一节。

## 2. 架构

### 2.1 模块与数据流

数据流向：外部站点 → `crawler` → `raw_*` 表 → `pipeline` → `cleaned_*` 表 → `analysis` → `result_*` 表 → `viz`。

| 模块 | 职责 |
| --- | --- |
| `crawler` | 采集外部数据，导入现成的真值表 |
| `pipeline` | 清洗、截止日对齐、特征构造、样本划分 |
| `analysis` | 信号 A/B、融合、置信标签、评估、全量拟合 |
| `viz` | 图表、单款查询页 |

原则：

- 依赖单向流动，下游只读上游产物，不回写，也不反向调用。只有 `crawler` 发网络请求。
- `common` 在最底层，四个模块都可以导入它；它不导入任何业务模块，也不放业务规则。项目根目录与各固定路径只在 `common` 中定义一次。
- 截止日截断、样本划分等规则在 `pipeline` 中只实现一次，各处复用。
- 三层数据都在同一个 SQLite 数据库 `data/steam.db` 中，用表名前缀 `raw_`、`cleaned_`、`result_` 区分。`raw_*` 永不删除；其余两层和模型文件都是派生数据，删掉后依次运行 `pipeline`、`analysis`、`viz` 即可重建。
- 数据过滤不静默丢行，每条规则都写日志。

目录结构：

```
crawler/   pipeline/   analysis/   viz/   # 四个模块；各脚本入口为 python -m 模块.脚本，模块本身没有入口
  crawler/sources/                       # 一个数据源一个文件，入口为 python -m crawler.sources.<数据源>：ars、itad、review_counts、reviews、store_items
  pipeline/ 现有脚本                      # games、prices、review_counts；样本表是一个包 pipeline/samples/，入口为 python -m pipeline.samples
  viz/ 现有脚本                           # k_by_reviews、reviews_vs_players、method_comparison
  analysis/                              # evaluation（读训练样本、分折、算误差）、model_inputs（样本表转模型输入）、baselines（固定倍数、线性回归两个对照）
  crawler/ 其余文件                       # 各数据源共用的采集基础设施：请求、采集日志
common/                                  # 各模块共用的小工具：路径、日志、时间；不含业务逻辑
query/                                   # 单款查询入口（未实现）
tests/                                   # 采集、清洗、画图的单元测试；数据泄露测试待建样本表后补
data/                                    # steam.db、models/、logs/ 的内容不入 git（除 raw_* 外可重建）；data/source/ 的原始 CSV 入 git
figures/                                 # 生成的图，不入 git；dataflow.html（数据流图）除外
docs/                                    # 设计、推导、devlog
```

技术栈：Python 3.11+、`requests`、`pandas`、`numpy`、`scipy`、`scikit-learn`、SQLite、`matplotlib`、Plotly。

### 2.2 数据表

下列字段为初始设计，命名沿用早期探索版本（正式开发前的旧仓库原型）；实现时以代码中的表结构为准；表名后标（未实现）的还没建。日期用 `YYYY-MM-DD`（月份为 `YYYY-MM`），时刻用 `YYYY-MM-DD HH:MM:SS`（UTC，表里标明 Unix 秒的除外），金额统一为美元。raw 表每行另带采集或导入时间 `fetched_at`，只有 `raw_store_tags`、`raw_tag_names`、`raw_reviews` 三张例外。

**raw：一个数据源一张表，原样保存。**

| 表 | 主键 | 字段 |
| --- | --- | --- |
| `raw_ars_players_2018` | `appid` | `title`、`players` |

| `raw_charts_monthly`（未实现） | `(appid, month)` | `avg_players` |
| `raw_itad_ids` | `appid` | `itad_id`（ITAD 的游戏编号，未收录时为空）；查历史价格前先用它把 `appid` 换成 ITAD 编号 |
| `raw_price_history` | `(appid, country, changed_at, regular, price)` | 一次价格变动一行，只记变动之后的状态：`currency`、`price`（实付价）、`regular`（当时的标价，不打折时卖多少）、`cut`（折扣百分比）、`fetched_at`。有的游戏 ITAD 同时跟踪两个 Steam 购买项，同一时刻有两条原价不同的记录，接口不标明属于哪个购买项，所以主键带上 `regular` 和 `price`，两条都存，选哪条留给 `pipeline`。不存“上一个价格”和“结束时间”：上一个价格就是上一行的 `price`，一条记录的状态持续到下一条记录的 `changed_at` 为止。`changed_at` 为变动时刻，入库时统一换成 UTC；`country` 暂时只采 `US`；存全部历史，截止日筛选留给 `pipeline`。只存 Steam 商店（ITAD 商店编号 61）的记录 |

| `raw_crawl_log` | `(source, request_key)` | `status`（处理结果，取值见表后说明） |

`source` 有 5 个值，`request_key` 的格式各不相同：`store_items`、`itad_ids`、`itad_history` 是 `<appid>`；`review_counts` 是 `<appid>|<cutoff_date>|<query>`；`reviews` 是 `<appid>|<cutoff_date>|<window>`。`status` 里 `200`、`未收录`、`空结果` 是有定论的，重跑不再请求；`parse_error`、`result_<n>`、`timeout`、`network`、`bad_json` 和其他 HTTP 状态码算失败，重跑会重试。

**result：分析结果，`viz` 只读。**

| 表 | 主键 | 字段 |
| --- | --- | --- |
| `result_estimates`（未实现） | `sample_id` | `ln_a`、`ln_b`、`b_unavailable_reason`、`ln_fused`、`sigma`、`lower`、`upper`、`divergence`、`label`（高 / 中 / 低）；`calib` 样本存留一法预测，不存全量拟合后的预测；`train` 样本不写入 |
| `result_params`（未实现） | `name` | `value`；`name` 取 `a`、`b`、`beta`、`gamma0`、`delta`、`eta`、`sigma_a`、`sigma_b`、`mu_b`、`sigma_fused`，含义见“最终模型”一节 |
| `result_feature_importance`（未实现） | `feature` | `importance`；树模型的特征重要性，供 `viz` 画图 |
| `result_cv_scores` | `(experiment, variant)` | 五折交叉验证的成绩，一种做法一行：`n_samples`（参加五折的游戏款数）、`rmse`（$\ln k$ 的均方根误差）、`hit_rate`（$\pm 30\%$ 命中率，存小数） |
| `result_cv_predictions` | `(experiment, variant, sample_id)` | 五折交叉验证里每款游戏的预测：`true_ln_k`（真值）、`predicted_ln_k`（预测值）；只有要画误差分布的比较才写，其余比较只写成绩 |

两张 `result_cv_*` 表记录训练阶段的比较，`result_estimates` 不存 `train` 样本，所以另建。`experiment` 是哪一次比较（回答一个问题），`variant` 是这次比较里的哪一种做法，都用英文代号，画图时由 `viz` 换成中文。同一个 `experiment` 的几行只在要比的那一处不同，其余条件相同；不同 `experiment` 之间不直接比。重跑一个 `experiment` 时，在一个事务里删掉它的旧行再写新行，其他 `experiment` 不动；比较的过程和理由记在 devlog。`true_ln_k` 和样本表重复，仍然存下：`viz` 只读 result 表，不再自己算 $\ln k$。

| `experiment` | 比较的问题 | `variant` |
| --- | --- | --- |
| `methods` | 树模型比两个对照好多少 | `fixed`、`linear`、`tree` |
| `tree_size` | 每棵树最多几片叶子、种多少棵 | `leaves_<叶子数>_iter_<棵数>`，如 `leaves_31_iter_300` |
| `min_leaf` | 每片叶子至少多少款 | `min_<款数>_iter_<棵数>` |
| `min_reviews` | 训练集的评测数门槛 | `min_<条数>` |

### 2.3 单款查询

（未实现）入口为 `python -m query <appid>`，截止日默认为当天。输入 `appid` 后依次调用 `crawler` 采集这款游戏、`pipeline` 生成一条 `query` 样本、`analysis` 用已冻结的模型和参数估算、`viz` 输出结果和查询页。查询只做预测，不重新拟合；命中排除条件（如不是游戏）时说明原因并结束；免费游戏照常估算，但只输出玩家数，不换算成销量。`query` 只负责按顺序调用，不含计算逻辑。

## 3. 数据

### 3.1 数据源

不爬取 SteamDB，其 FAQ 明确禁止爬取。

| 数据 | 来源 | 用途 |
| --- | --- | --- |
| 商店信息 | Steam `IStoreBrowseService/GetItems` 接口（一次可查多款；只能取当前价格）；标签名来自 `IStoreService/GetTagList` | 是不是游戏、标签、发售日、是否免费、当前原价 |
| 评测计数 | Steam `GetAppReviews` 接口的汇总数 | 截止日前的评测总数、好评、Steam 内购买、政策后、各语言，均为精确值 |
| 评测抽样 | Steam `GetAppReviews` 接口：截止日前按时间分 5 段，每段取该段最新的至多 100 条 | 评测者时长中位数，供信号 A 的特征和信号 B |
| 月度在线人数 | SteamCharts（第三方在线人数统计站） | 信号 B |
| 历史价格 | IsThereAnyDeal（ITAD）接口的价格变动记录，只取 Steam 商店、美国区；重新采集，不沿用早期探索版本的价格表 | 截止日原价（为 0 即免费）、平均实付价格、三档折扣时间占比 |
| 训练真值 | Ars Technica 2018-07-01 玩家数表 | 训练集 |
| 近年真值 | 已人工核对的近年真值表，每款一条 | 校准/测试集 |

### 3.2 采集

- 按站点限速；请求设超时，遇到限流或服务器错误时退避重试。
- 采集结果直接写入 `raw_*` 表，中断后重跑同一命令即可从断点继续，已有数据不重复请求。
- 评测计数请求量大（每款 15 次），可以几路同时发请求：`python -m crawler.sources.review_counts --workers 路数`。发请求由线程池做，写库只由主线程做；限速对所有线程合计。
- 商店信息用批量接口采集：一次请求查 200 款（实测 400 款会被拒绝），全部一万三千多款约 70 次请求。原先用的 `appdetails` 接口一次只能查一款，且按 IP 限流（实测约每 5 分钟 200 次），全量要 5 个多小时，已停用。
- 已从商店下架的游戏，评测接口返回为空，在 `raw_crawl_log` 记“未收录”，不写数据行，重跑时不再请求。
- 评测只取两类数据：限定在截止日前的计数（汇总数，不翻页），以及少量抽样评测。
- 评测抽样按时间分层：从上架时刻到截止日平均切成 5 段，每段请求一次，拿回这一段的评测总数和最新的至多 100 条（一页的上限），每款 5 次请求。第一段的起点用 1，抢先体验期间等早于上架时刻的评测也算进去；上架时刻取 `raw_store_items.release_ts`，缺失、晚于截止日或早于评测系统上线时从 2013-10-01 算起（评测系统 2013 年 11 月上线，切段起点保守取 2013-10-01）。相邻两段首尾不重叠。接口只能按时间、有帮助程度排序，做不到真随机；只取截止日前最新的 100 条会只看到截止日前不久的评测者，老游戏偏差很大（实测见 devlog 2026-11-13）。
- 抽样评测里的 `playtime_forever` 是采集当天的总时长，包含截止日之后的游玩，不用于任何计算。
- 在线人数只用截止日所在月之前的整月。
- 历史价格来自 ITAD，需要 API 密钥，放在本地 `.env` 里，不进仓库。接口默认只返回最近 3 个月，请求时要显式给一个足够早的起始时间。ITAD 不认 Steam 的 appid，先批量换成 ITAD 编号（一次 200 款），再逐款查历史。限额为 5 分钟 1000 次。

已知偏差：已删除的评测和被封账号的评测在接口中已不存在，重建出的历史评测数偏少，对 2018 训练集影响更大。2013 年前上架的游戏，评测系统上线前的玩家没有评测，分段抽样也代表不了他们；评测系统刚上线时来写评测的多是玩了多年的老玩家，时长偏长。评测抽样每段只取最新的 100 条，不是段内随机：截止日前评测不少于 10 条的游戏里，38% 至少有一段没抓全，没抓全的段里抽到的评测只覆盖这一段最后约 12% 的时间（中位数），时长偏低；切成 20 段对比，10 款老游戏多在 10% 以内，最多 13%（实测见 devlog 2026-11-13）。训练集里游戏越老 $k$ 越大（不到 3 个月的中位数约 29，7 年以上约 224），其中年龄超过约 4.7 年的游戏恰好都是评测系统上线前上架的，年龄的作用和“早期玩家没有评测”混在一起；校准集截止日更晚，同样年龄的游戏没有这个效应，这一部分只能靠校准吸收。

### 3.3 清洗与训练集门槛

- 只按输入侧条件筛选，不按 $k$ 或真值筛选。排除非游戏、零评测、重复、上架晚于截止日的样本。免费游戏保留，用“截止日原价为 0”表示，不另设免费标签。
- 是否免费按截止日当时判断：历史价格里截止日的原价为 0 即免费；查不到时留空，不用商店信息里的 `is_free`（那是采集当天的状态）。
- 上架日取商店上架时刻、最早上架时刻、抽到的最早评测时刻三者里最早的。抢先体验转正式版、老游戏重新上架时，商店的上架时刻会被改成后来的日期；只用它的话，截止日时还在抢先体验的游戏会被当成“上架晚于截止日”排除（2018 年训练集里有 449 款）。最早上架时刻不是每款都有，所以再拿抽到的最早评测兜底；它不一定是真正的第一条（第一段超过 100 条时只抓了最新的 100 条），日期可能偏晚。
- 商店信息是采集当天的状态。会随时间变的内容不能当作截止日的情况，要换用带时间的来源：是否免费看历史价格，是否在抢先体验看发行日与评测日期。因此标签里的 `Early Access`、`Free to Play` 这类状态词在清洗时去掉。
- 游戏的分类用标签，不用开发商填的类型（genres）。标签由开发商先设、玩家投票修正，Steam 自己的推荐和“类似游戏”也按排名前 20 的标签计算；类型只有十来种，区分度低。标签的权重是采集当天的数，会随时间增长，只用来排序和取前几个，数值本身不作特征。
- 清洗结果只保留能用的行：没有发行日的游戏不写入 `cleaned_games`，记日志。
- 评测计数清洗只排除评测数为 0 的游戏：截止日前一条评测都没有，$k$ 无从算起。评测数门槛（如不足 10 条）会随交叉验证调整，不放在清洗表，放在建样本表时。
- 近年真值表人工筛选时，只收录评测数足够、截止日不早于 Steam 评测系统上线（2013 年 11 月）的游戏；`pipeline` 再校验一次，不符合的剔除并写日志。
- 历史价格缺失或截止日之后才开始的游戏不删除，价格特征全部留空，交给模型处理，不用商店当前原价兜底：它是采集当天的价格，和截止日原价只有约 68% 一致；商店现在标为免费的 798 款里，有 286 款截止日时并不免费。训练集里这样的游戏约 51 款。
- 同一时刻有两条原价不同记录的游戏（ITAD 同时跟踪两个购买项或偶尔插进别的购买项），`cleaned_prices` 两条都留，建样本表时再定取哪一条。暂定取原价与前一时刻相同的那条，接不上时看后一时刻；都接不上的计数写日志。
- 有少数几组 appid 被 ITAD 归到同一个游戏编号下，查到的是同一份价格历史；建样本表时要注意它们的价格特征不是各自独立的。
- 评测者时长中位数按段加权：只用有 `playtime_at_review` 的评测，每条的权重为这一段的评测总数除以这一段有时长的条数，再取加权中位数；这样各段权重之和正好等于该段评测总数。整段抽到的评测都缺时长的段跳过（训练集里 27 段）。
- 价格特征只从第一条价格记录算起，之前的价格未知，不假设为原价。持续过久的折扣多半是漏记了“恢复原价”，建样本表时截断，阈值是可调参数（暂定 30 天，实测 99% 的折扣不超过 28 天）；`cleaned_prices` 只存实际持续天数，不截断。

训练集的评测数门槛（暂定，供参考，具体做法到建样本表时再定）：评测 1 到 9 条的游戏不进训练，因为评测数是整数，多一条评测 $k$ 就大幅变化，属于模型学不了的噪声。更高的门槛不预先设定，到训练时用几个候选值做交叉验证比较。原先“评测数 $\ge 500$”的设定不再作为默认，它的依据之一“真值抽样截掉了小游戏”与 Ars 表的实际情况不符（见 devlog 2026-11-11）。评测少的游戏仍按原思路处理：评测数进树模型（见“样本表”一节），校准中的 $\ln R$ 项先保留、由留一法决定去留，评估时大小游戏分开报告，在置信标签中降档（置信标签一节的 500 暂时沿用）。

### 3.4 样本表

`cleaned_samples` 一款游戏一个截止日一行，汇总各清洗表，字段见“数据表”一节。特征分四类，按数据源分：商店信息、评测计数、评测抽样、历史价格。逐类定下来后写在这里。

商店信息这一类特征只有游戏年龄和标签。年龄用截止日减上架日（单位年），不用上架年份：校准集里会有 2019 年以后上架的游戏，这些年份训练时一款都没见过，而年龄的范围训练时都见过；线性回归对照里取对数。标签在样本表里只存一列 `tags`，和 `cleaned_games.tags` 一样是用 `|` 连起来的一串，这样训练只读样本表一张表；训练时再展开成 0/1 列，有这个标签记 1：默认用每款的全部标签（最多 20 个），训练集里至少 100 款游戏有的标签才单独成列（约 192 列），树模型和线性回归用同一套列。标签权重是采集当天的票数，只用来排序，不作数值。“取前几个标签”和“至少多少款”在代码里是参数；选出的标签清单随模型一起保存，查询时按同一份清单、同样的顺序展开。不用标签个数：它和 $\ln R$ 的相关系数约 0.5，和 $\ln k$ 几乎无关（约 −0.03），加进去只会带进采集当天的人气。

评测计数这一类：评测数 `total_reviews`、好评率、Steam 内购买占比、各语言占比。

- 评测数进树模型。预测时它是已知的；训练集里评测 10 到 19 条的 $k$ 中位数约 41，500 条以上约 90 到 94，评测少时好评率和各种占比也不可靠，模型要看到评测数才知道该信它们几分。评测数也是 $k$ 的分母，碰巧多几条 $k$ 就偏小，但预测时面对的也是看到的评测数，这层关系应该学进去。校准里的 $\eta \ln R$ 照旧保留：训练真值是玩家数、校准真值是销量，2019-11 后 Steam 又提示写评测，两边评测数和 $k$ 的关系可能不同；留一法下 $\eta$ 接近 0 或误差不降就删。线性回归对照里取对数。
- 好评率直接用，不平滑：好评率 95% 以上的游戏 $k$ 明显偏低，在评测上千条的游戏里也一样（$k$ 中位数约 64，60% 到 80% 的约 105），不是评测少造成的粗糙。好评率和 $k$ 的关系是两头低中间高，线性回归学不了，树可以。
- Steam 内购买占比原样用，是这一类最强的特征：低于 40% 的 $k$ 中位数约 153，90% 以上约 51；评测多来自激活码、慈善包、赠送的游戏，拥有者很少写评测。免费游戏没有购买这一步，占比中位数只有约 5%，含义和付费游戏不同，但不另设规则，由树结合截止日原价（为 0 即免费）自己区分。
- 语言在样本表里存 13 种语言各自的占比和 13 种之外的占比，共 14 列，不在表里合并。训练时默认合并成 9 列：英语、俄语、中文（简繁）、德语、法语、西语（含拉美西语）、巴西葡语、小语种合计（日、韩、波兰、土耳其）、13 种之外。拉美西语一定并入西语：2018 年以前它几乎为 0，模型学不到，以后的年份却不为 0。怎么合并在代码里是参数。各语言占比与 $\ln k$ 的相关系数都在 0.15 以内，作用不大。线性回归对照里去掉英语一列，否则几列加起来等于 1，系数算不出。
- 不用好评数、Steam 内购买评测数、各语言评测数这类原始计数：它们是评测数乘占比，重复。

评测抽样这一类只有评测者时长中位数 `playtime_median_hrs` 进模型，存小时原值，线性回归对照里取对数。单看它和 $\ln k$ 几乎无关（相关系数约 0.04），因为它和评测数纠缠（与 $\ln R$ 相关约 0.55）；按评测数分层后信号出来了：评测 200 到 999 条的游戏里，时长中位数不到 1 小时的 $k$ 中位数约 116，20 小时以上约 70，玩得越久 $k$ 越小。信号 B 也要用这一列。

- 不存时长均值：最少只抽到 10 条，一个挂机几千小时的评测者就能把均值带偏，而且和中位数重复。
- `sample_n` 存进样本表但不进模型、也不设门槛：它几乎由评测数决定，和评测数重复，也说不出和 $k$ 的关系；中位数横跨 0.2 到 45 小时，十来条造成的抖动相对很小，置空反而让信号 B 用不了。只用于事后查误差。
- 不用 `playtime_forever`：含截止日之后的游玩。也不为段内只取最新造成的偏低做手工修正：训练和预测用同一套抽样，偏差一致。

历史价格这一类进模型的有五列：截止日原价、平均实付价格、折扣不低于 25%、50%、75% 的时间占比，都只用截止日之前的价格段，从第一条记录算起，单段折扣超过 30 天的超出部分按原价算。

- 截止日原价取原价不取实付价：2018-07-01 正好在 Steam 夏季大促期间（6 月 21 日到 7 月 5 日），训练集里约 75% 的游戏当天在打折，实付价反映的只是那天打不打折。免费就是 0，不另设免费标签；免费游戏的 $k$ 中位数约 171，付费各档在 60 到 78 之间。
- 平均实付价格按天数加权，免费期间为 0，把调价、先付费后免费、常打折都揉进一个数。它和截止日原价相关约 0.95；保留两者，是因为截止日前不久才转免费的游戏（训练集 93 款），平均实付价格仍大于 0，只有原价能看出当时免费。
- 折扣分三档：只用 75% 一档时，同龄游戏里折扣越多 $k$ 越大（上架 1 到 3 年的，从不深度打折约 68，深度折扣占比 20% 以上约 256），不是年龄的影子；去掉夏季大促那几天重算，结果不变。三档合起来能看出是小打小折还是经常大甩卖。
- 临时脚本的五折对比（只用评测数、好评率、Steam 内购买占比、年龄四个基础特征，见 devlog 2026-11-13）：不加价格误差 0.830；只加原价 0.799；只加平均实付价格 0.791；原价加 75% 一档 0.784；平均实付价格加三档 0.765；再加原价 0.762。30 天截断与不截断的误差几乎相同，截断是为了纠正 ITAD 漏记“恢复原价”造成的长折扣（最长一段 5103 天），不是为了提高成绩。阈值 30 天在代码里是参数。
- 不用：任意折扣的时间占比（与 $k$ 关系很乱）、截止日当天是否打折（大促造成的假象，校准集分布完全不同）、价格来源（不再兜底后只剩一种取值）。

## 4. 方法

### 4.1 信号 A：评测倍数模型

信号 A 基于“评测数 $\times k$”估算销量，分为树模型训练与线性校准两步。

第一步，在训练集上用树模型学习对数倍数 $\ln k$。模型输入为全部特征：评测数、截止日原价、好评率、标签、游戏年龄、Steam 内购买占比、各语言评测占比、三档折扣时间占比、平均实付价格、评测者时长中位数等。政策后评测占比在训练集上恒为 0，不作为树模型的输入，只用于第二步校准。模型和特征只在这一步选择，用五折交叉验证。特征重要性也在这一步输出。

树模型用 scikit-learn 的梯度提升回归（`HistGradientBoostingRegressor`）：一棵接一棵地种树，每棵专门修正前面那些树的误差。目标是 $\ln k$ 而不是直接学 $\ln$ 玩家数：评测数也是输入时两者的误差相同，但树模型不会外推，直接学玩家数会严重低估比训练集都大的游戏（实测见 devlog 2026-11-13）。损失取平方误差，衡量的是“差几倍”而不是“差几份”，与命中条件一致。缺失的特征在样本表里存空，不填补，由模型直接处理。超参数只比较三个，用五折交叉验证选：

- 每棵树最多几片叶子：15、31、63。
- 树的棵数：最多种到 1000 棵，取 50、100、200、300、500、700、1000 这几个点。每种叶子数各画一条“棵数 → 误差”曲线，各自找最低点再比：大树种得少就够、小树要种得多，先在一种叶子数下定棵数再比大小，会偏向那一种。每折只训练一次，用 `staged_predict` 取出种到各个棵数时的预测。
- 每片叶子至少多少款：20、50、100，在选定的叶子数和棵数下比较。

学习率固定 0.1：再降只换来很小的改善，时间却成倍增加。提前停止关掉：它会随机留一部分教材当验证，而且样本过 1 万款才自动打开，结果不好比。选择规则在看结果之前定好：默认参数（31 片叶子、100 棵、每片至少 20 款）的那个点必须与下文三种方法对比表里的 0.703、45.3% 完全一致，对不上先查原因；几种设置的均方根误差相差不到 0.005 时，取树少、树小的那个。评测数门槛不在这里比：门槛不同，参加打分的游戏就不同，要另定在同一批游戏上打分的比法。

样本表的列怎么变成模型输入，在代码里留成参数。先跑默认方案得到基线，之后每次只改一项，用五折交叉验证和基线比：

| 参数 | 默认 | 训练时比较 |
| --- | --- | --- |
| 评测数门槛 | 至少 10 条 | 几个更高的候选值 |
| 标签：至少多少款游戏有才单独成列 | 100（约 192 列） | 500（约 52 列） |
| 标签：每款取前几个 | 全部（最多 20 个） | 5（约 78 列） |
| 语言怎么合并 | 9 列 | 不用语言；只合并西语、其余全拆开（13 列） |
| 评测者时长中位数 | 用 | 不用 |
| 折扣超过多少天截断 | 30 天 | 不比（截 30 天、60 天、不截，实测误差几乎相同） |

默认方案下树模型的输入约 211 列：游戏年龄 1 列、标签约 192 列、评测数、好评率、Steam 内购买占比各 1 列、语言 9 列、评测者时长中位数 1 列、价格 5 列。`p_post` 只用于校准，`sample_n` 只作记录。

另设两个对照，树模型要明显优于它们才说明学到了东西：一是所有游戏用同一个倍数（训练集 $\ln k$ 的平均值）；二是线性回归，每个特征乘一个系数再相加，缺失的特征用训练集的中位数填补（只在这个对照里填）。标签清单用全部训练样本选一次，不分折重选：选标签只数款数，不看 $\ln k$。三种方法用同一套五折，结果如下（评测 10 条以上 9623 款；树模型暂用默认参数，参数比较后更新）：

| 方法 | 输入列数 | 均方根误差 | $\pm 30\%$ 命中率 |
| --- | --- | --- | --- |
| 固定倍数 | 0 | 1.018 | 26.1% |
| 线性回归 | 210 | 0.824 | 36.3% |
| 树模型 | 211 | 0.703 | 45.3% |

第二步，训练真值是玩家数，与销量口径不同，因此在校准/测试集上（按游戏留一法）对树模型输出做少变量线性校准：

$$
\ln k_{\text{true}} = \beta \cdot \ln k_{\text{tree}}(x) + \gamma_0 + \delta \cdot p_{\text{post}} + \eta \cdot \ln R
$$

其中 $\ln k_{\text{tree}}(x)$ 为树模型输出，$p_{\text{post}}$ 为评测政策变化后的评测占比，$R$ 为评测数；$\beta$、$\gamma_0$、$\delta$、$\eta$ 依次为缩放、截距、政策项、评测数项系数，各项含义见 [DERIVATIONS.md](DERIVATIONS.md)“校准公式”一节。

校准只用这 4 个系数，不加其他特征的修正项。原因是校准样本只有一百多条，多加特征会过拟合，也会和树模型已学到的特征作用互相抵消。训练集的截止日都在政策变化之前（$p_{\text{post}} = 0$），树模型学不到政策的影响，所以政策项必须放在校准里。

评测政策变化日期固定为 2019-11-01。依据是早期探索版本对 40 款老游戏月度评测量的实测：评测指数中位数在 2019-11 由约 0.95 跳到约 3.3，此后持续保持。

校准后，信号 A 的销量估计值为 $\hat{S}_A = R \cdot e^{\ln k_{\text{true}}}$。

### 4.2 信号 B：在线人数模型

信号 B 来自早期探索版本，利用总游玩小时除以人均游玩小时估算销量。

第一步，计算累加到截止日所在月前一个月的总游玩小时 $H$：

$$
H = \sum_{m} c_m \cdot d_m
$$

其中 $H$ 为总游玩小时，$m$ 为统计月份（累加到截止日所在月的前一个月），$c_m$ 为第 $m$ 个月的月均在线人数，$d_m$ 为第 $m$ 个月的当月小时数（上架当月只按上架后的天数计算）。

第二步，根据评测者时长中位数计算人均游玩小时 $h$：

$$
\ln h = a + b \cdot \ln t_{\text{med}}
$$

其中 $h$ 为人均游玩小时，$t_{\text{med}}$ 为抽样评测的 `playtime_at_review` 中位数，$a$ 和 $b$ 为回归参数。参数 $a$、$b$ 在训练集上拟合（目标为总小时除以真实玩家数），另做五折交叉验证。评测时长偏低（玩家写完评测后继续游玩）的平均影响由这一步拟合吸收。不用 `playtime_forever`：它包含截止日之后的游玩，而 $H$ 只累加到截止日，两者口径不一致。

第三步，计算信号 B 的输出 $\hat{S}_B$：

$$
\hat{S}_B = \frac{H}{h}
$$

其中 $\hat{S}_B$ 为信号 B 的销量估计值。三步公式的来源见 [DERIVATIONS.md](DERIVATIONS.md)“信号 B”一节。

只有在线人数从上架初期就有记录、且截止日前已积累足够记录时才计算 B，否则只用 A；具体条件在代码中设定。累计漏掉上架初期会严重低估 $H$。信号 B 的覆盖率有限，早期探索版本约一半真值可用，销量低于 1 万的游戏几乎不可用。

### 4.3 信号融合

每路信号 $i \in \{A, B\}$ 的误差 $\sigma_i$ 取该路留一法对数残差的标准差，是一个固定值，不随单款游戏变化。在对数空间按固定权重 $w_i = 1/\sigma_i^2$ 加权融合：

$$
\ln \hat{S} = \frac{w_A \ln \hat{S}_A + w_B (\ln \hat{S}_B + \mu_B)}{w_A + w_B}
$$

其中 $\ln \hat{S}$ 为融合后的对数销量估计值，$w_A$、$w_B$ 分别为信号 A 和信号 B 的权重，$\mu_B$ 为信号 B 的残差均值修正项。信号 A 已经校准，不加修正项，所以只有 A 时结果等于 A；信号 B 没有在真值上校准，要加 $\mu_B$。缺少的信号不参与计算，融合结果总在可用信号之间。

$\sigma_A$、$\sigma_B$、$\mu_B$ 都在留一法中计算：预测某款游戏时，只用其余游戏的残差。

预测区间使用的 $\sigma$ 同样取固定值：两路都可用的样本取融合结果留一法残差的标准差，只有 A 的样本取 $\sigma_A$。两路共享评测者时长、误差不独立，直接取融合结果的残差就不必单独估计两路的相关程度。区间的实际覆盖率在评估中检验，如实报告，不足时也不事后放宽：放宽多少要看全部结果才能定，放宽后再报覆盖率就成了自己证明自己。推导见 [DERIVATIONS.md](DERIVATIONS.md)“融合”一节。

### 4.4 置信标签

权重无法反映单款游戏上某一路信号是否离谱，因此由置信标签提示分歧。两路信号的分歧 $D$ 定义为：

$$
D = \left| \ln \hat{S}_A - (\ln \hat{S}_B + \mu_B) \right|
$$

分歧阈值取固定值 $\tau = 0.5$，即两路估计相差约 1.65 倍。该值在看到留一法结果之前确定，之后不按结果调整。

| 信号 B 可用性 | 分歧程度 | 评测数条件 | 置信标签 |
| --- | --- | --- | --- |
| 有 B | 分歧小（$D \le \tau$） | 评测 $\ge 500$ | 高 |
| 有 B | 分歧小（$D \le \tau$） | 评测 $< 500$ | 中 |
| 有 B | 分歧大（$D > \tau$） | 不限 | 低 |
| 无 B | 不涉及 | 评测 $\ge 500$ | 中 |
| 无 B | 不涉及 | 评测 $< 500$ | 低（外推） |

两路分歧大时，融合的命中率可能低于单路，但事先无法判断该信哪一路，因此不改融合公式，由“低”标签提示，原因见 [DERIVATIONS.md](DERIVATIONS.md)“估计值在中间，命中率不一定在中间”一节。作为参考，早期探索版本中分歧最大的 $1/4$ 样本命中率约 29%，其余约 59%。

## 5. 评估与测试

### 5.1 评估方法

对校准/测试集中的每一款游戏做留一法：把它拿出来，用其余游戏拟合校准系数、$\sigma_A$、$\sigma_B$ 和 $\mu_B$，然后分别预测信号 A、信号 B 和融合结果，把这三个预测与真值比较。被测游戏不能出现在任何拟合数据里。留一法只用来评估，产出的是一组成绩，不产出最终使用的参数。

### 5.2 最终模型

评估完成后，用全部数据重新拟合一次，得到交付使用的最终模型，称为全量拟合：

- 树模型与信号 B 的 $a$、$b$：用全部训练集拟合。超参数和特征沿用五折交叉验证选定的结果，不再调整。
- 校准系数 $\beta$、$\gamma_0$、$\delta$、$\eta$：用全部校准/测试集拟合。
- $\mu_B$、$\sigma_A$、$\sigma_B$ 和融合区间的 $\sigma$：取全部校准/测试集上的留一法残差计算。

全量拟合的结果保存后即冻结：单款查询和展示都只读这份结果，不再拟合。报告中的准确度一律引用留一法的成绩，而不是全量拟合后在同一批数据上的成绩，因为后者用到了被测游戏本身，会偏乐观。

### 5.3 比较指标

- 主指标：$\pm 30\%$ 命中率，按信号 A、信号 B、融合分别报告，并按销量档和置信标签分组报告。
- 辅助指标：95% 区间的实际覆盖率。
- 选模型指标：$\ln k$ 的均方根误差 $\sqrt{\frac{1}{n}\sum_i (\widehat{\ln k_i} - \ln k_i)^2}$。五折交叉验证选模型、选参数时用它，因为它对每一点改进都敏感；命中率只看是否落在 $\pm 30\%$ 以内，差 1.5 倍和差 10 倍算一样，用来报告成绩，不用来选。
- 命中率和覆盖率都是比例，95% 置信区间用 Wilson 区间公式直接计算，推导见 [DERIVATIONS.md](DERIVATIONS.md)“比例的置信区间”一节。

### 5.4 测试

测试分两部分。

已有的单元测试覆盖采集、清洗、画图，只保留真实数据会触发的行为，如重复行、续传、重试，不为不会出现的坏数据造测试。

泄露测试是计划中的，建好样本表后补，只检查一件事：数据不能泄露。包括：特征的时间不晚于截止日；`playtime_forever` 不进入任何特征；训练集不含校准/测试集的 `appid`；被测游戏不参与自己的预测；单款查询不改变已拟合的模型和参数。

### 7.2 候选改进

主线跑通后再考虑，按需取用。先只用主线特征得到基线，之后每次只试一项并与基线对照。加特征遵守三条：说得出它为什么会改变 $k$；同一件事只留一个代表；交叉验证没有明显改善就不留。

| 方向 | 说明 |
| --- | --- |
| 耐玩度 | 抽样评测时长的均值与中位数之比，加入信号 B 的人均时长拟合。早期探索版本数据上能减小 B 的误差，但没有提高命中率。用于信号 A 时，它与 $\ln k$ 的相关系数约 0.11，可能只是抽得越多越容易碰上极端长时长；样本表不存均值，要试时从 `raw_reviews` 现算 |
| 评测时间线 | 首月评测占比、评测数的衰减速度等特征 |
| 更多价格特征 | 由同一份价格历史再算：任意折扣的时间占比、最大折扣、每年打折次数、永久降价幅度等；先在 `pipeline` 里算出来，留不留由交叉验证决定 |
| 慈善包与免费赠送 | ITAD 另有慈善包和免费赠送记录（带起止时间），这类拥有者很少写评测，可能抬高 $k$；需新增两张 raw 表，老记录是否齐全尚未核实。与 Steam 内购买占比有重叠；慈善包要区分主打与陪衬（可用所在档位价格等间接指标），先试慈善包 |
