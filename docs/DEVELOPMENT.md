# 开发文档

本文是项目设计文档，修改设计前需先更新本文。项目推进过程中的决策与问题记录在 [devlog.md](devlog.md)，文中公式的推导见 [DERIVATIONS.md](DERIVATIONS.md)。

## 1. 背景信息

### 1.1 目标与背景

项目名称为 `steamsales-estimator`。项目目标是用公开数据估算单款 Steam 游戏的销量（只针对付费游戏），输出估计值、95% 区间、置信标签和可复查的计算过程。

本项目的方法参考 Gamalytic 公开的三篇文章。销量估算基于销量等于评测数乘以倍数 $k$ 的基本关系：

$$
S = R \cdot k
$$

其中 $S$ 为游戏销量（即真值），$R$ 为评测数，$k$ 为单条评测对应的销量倍数。倍数 $k$ 因游戏而异，受价格、年代、类型、好评率、折扣习惯等因素影响。项目的工作流程依次为：采集数据、估计 $k$、检验可信度、展示结果。

基于评测数的预测称为信号 A。为使估计更准，另用同时在线人数估算销量，称为信号 B。两路估计在对数空间按各自的整体误差加权融合。

**方法依据**

| 文章 | 本项目采用的内容 |
| --- | --- |
| [A new way to estimate steam game sales](https://gamalytic.com/blog/a-new-way-to-estimate-steam-games-sales)（2023-01-20） | 信号 B 的思路：由同时在线人数累计总游玩小时，再除以人均游玩时长得到玩家数。 |
| [What makes people review your game? A deep dive into the Steam's sales/review ratio](https://gamalytic.com/blog/a-deep-dive-into-the-steam-review-ratio)（2023-07-23） | 信号 A 的特征选取：发售时间（含 2019 年 Steam 提示写评测后倍数减半）、价格与折扣、好评率、评测者游玩时长、类型标签、评测数量。 |
| [How to accurately estimate Steam game sales](https://gamalytic.com/blog/how-to-accurately-estimate-steam-sales)（2023-05-13） | 多种估计加权合并的思路；用 2018 年泄露数据集校正老游戏；以“误差 10%/30%/50%/70% 以内的比例”评价；评测数乘固定倍数的基线；有公开销量的对照表（校准/测试集来源之一）。 |

本项目没有采用的内容：畅销榜排名法、抽样公开玩家资料法、收入估计。与 Gamalytic 做法的具体差别（如在线人数取月均值而非逐小时、时长取评测者中位数并经拟合换算）见“方法”一章。

### 1.2 术语

样本，定义为一款游戏加一个截止日。截止日是样本全部输入数据截止的日期，一切输入只取截止日之前的数据。训练集的截止日为 2018-07-01；校准/测试集的截止日为销量公布日，或按“首日/首周/首月”换算的日期。

训练集（`train`）采用 2018-07-01 Ars Technica 公开的玩家数表，加上截至该日的评测数据，其真值是玩家数，非销量。校准/测试集（`calib`）采用已人工核对好的近年销量真值表，作为现成输入导入，每款游戏只保留一条最准的记录，真值是确切销量；同一批数据既用于校准，也用于留一法测试。不另设封存集。

评测数指截止日前所有语言的评测总数，包括非 Steam 内购买的评测；Steam 内购买占比作为单独特征输入模型。倍数 $k$ 定义为真值除以评测数，即 $k = S / R$。

单条样本预测命中的定义为相对误差不超过 30%：

$$
\left| \frac{\hat{S}}{S} - 1 \right| \le 0.3
$$

其中 $\hat{S}$ 为销量估计值。该条件在对数空间的形式见 [DERIVATIONS.md](DERIVATIONS.md)“命中条件”一节。

销量估计的预测区间定义为对数空间下的对称区间，名义覆盖率为 95%：

$$
\left[\, \hat{S}\, e^{-1.96\sigma},\ \hat{S}\, e^{1.96\sigma} \,\right]
$$

其中 $\sigma$ 为对数销量估计值 $\ln \hat{S}$ 的标准差。推导和成立条件见 [DERIVATIONS.md](DERIVATIONS.md)“预测区间”一节。

## 2. 架构

### 2.1 模块与数据流

数据流向：外部站点 → `crawler` → `raw_*` 表 → `pipeline` → `cleaned_*` 表 → `analysis` → `result_*` 表 → `viz`。

| 模块 | 职责 |
| --- | --- |
| `crawler` | 采集外部数据，导入现成的真值表 |
| `pipeline` | 清洗、截止日对齐、特征构造、样本划分 |
| `analysis` | 信号 A/B、融合、置信标签、评估、全量拟合 |
| `viz` | 图表、单款查询页 |

原则：

- 依赖单向流动，下游只读上游产物，不回写，也不反向调用。只有 `crawler` 发网络请求。
- `common` 在最底层，四个模块都可以导入它；它不导入任何业务模块，也不放业务规则。项目根目录与各固定路径只在 `common` 中定义一次。
- 截止日截断、样本划分等规则在 `pipeline` 中只实现一次，各处复用。
- 三层数据都在同一个 SQLite 数据库 `data/steam.db` 中，用表名前缀 `raw_`、`cleaned_`、`result_` 区分。`raw_*` 永不删除；其余两层和模型文件都是派生数据，删掉后依次运行 `pipeline`、`analysis`、`viz` 即可重建。
- 数据过滤不静默丢行，每条规则都写日志。

目录结构：

```
crawler/   pipeline/   analysis/   viz/   # 四个模块，入口为 python -m <模块>
  crawler/sources/                       # 一个数据源一个文件，入口为 python -m crawler.sources.<数据源>
  crawler/ 其余文件                       # 各数据源共用的采集基础设施：请求、采集日志
common/                                  # 各模块共用的小工具：路径、日志、时间；不含业务逻辑
query/                                   # 单款查询入口
tests/                                   # 数据泄露测试
data/      steam.db、models/、logs/       # 不入 git，可重建（raw_* 除外）
figures/                                 # 生成的图，不入 git；dataflow.html（数据流图）除外
docs/                                    # 设计、推导、devlog
```

技术栈：Python 3.11+、`requests`、`pandas`、`numpy`、`scipy`、`scikit-learn`、SQLite、`matplotlib`、Plotly。

下列字段为初始设计，命名沿用早期探索版本；实现时以代码中的表结构为准。时间统一用 `YYYY-MM-DD`（月份为 `YYYY-MM`），金额统一为美元，raw 表每行另带采集或导入时间 `fetched_at`。

**raw：一个数据源一张表，原样保存。**

| 表 | 主键 | 字段 |
| --- | --- | --- |
| `raw_ars_players_2018` | `appid` | `title`、`players` |
| `raw_store_items` | `appid` | `name`、`app_type`（接口给的数字代码：0 是游戏，6 是软件）、`is_free`、`release_ts`（在 Steam 上架的时刻，Unix 秒；未定档时为空）、`is_early_access`（采集当天是否在抢先体验）、`initial_price_usd`（当前原价；取购买项里第一个单独的包，不取捆绑包；免费或已停售时为空） |

| `raw_tag_names` | `tagid` | `name`（标签的英文名） |

| `raw_review_windows` | `(appid, cutoff_date, window)` | 评测抽样把截止日前的时间分成 5 段，一段一行：`window`（段号 1 到 5，按时间先后）、`start_ts`、`end_ts`（这一段的起止时刻，Unix 秒，两端都含）、`total`（这一段里的评测总数）、`fetched_at` |

| `raw_charts_monthly` | `(appid, month)` | `avg_players` |
| `raw_itad_ids` | `appid` | `itad_id`（ITAD 的游戏编号，未收录时为空）；查历史价格前先用它把 `appid` 换成 ITAD 编号 |
| `raw_price_history` | `(appid, country, changed_at, regular, price)` | 一次价格变动一行，只记变动之后的状态：`currency`、`price`（实付价）、`regular`（当时的标价，不打折时卖多少）、`cut`（折扣百分比）、`fetched_at`。有的游戏 ITAD 同时跟踪两个 Steam 购买项，同一时刻有两条原价不同的记录，接口不标明属于哪个购买项，所以主键带上 `regular` 和 `price`，两条都存，选哪条留给 `pipeline`。不存“上一个价格”和“结束时间”：上一个价格就是上一行的 `price`，一条记录的状态持续到下一条记录的 `changed_at` 为止。`changed_at` 为变动时刻，入库时统一换成 UTC；`country` 暂时只采 `US`；存全部历史，截止日筛选留给 `pipeline`。只存 Steam 商店（ITAD 商店编号 61）的记录 |

| `raw_crawl_log` | `(source, request_key)` | `status`（HTTP 状态或“未收录”“空结果”） |

**cleaned：清洗后的数据，一个样本的信息集中在一行。**

| 表 | 主键 | 字段 |
| --- | --- | --- |
| `cleaned_games` | `appid` | 只含游戏，一款一行：`name`、`release_date`（由商店时间戳按美国太平洋时间转成日期）、`release_date_source`（`store` 商店 / 第一条评测，后者待评测数据齐备后实现）、`tags`（标签名按权重从高到低用 `|` 连接，已去掉状态词）。没有发行日的游戏不写入，记日志 |

| `cleaned_charts_monthly` | `(appid, month)` | `avg_players` |
| `cleaned_samples` | `sample_id` | 样本：`appid`、`cutoff_date`、`split`（`train` / `calib` / `query`）、`truth_value`（`query` 为空）<br>评测：`total_reviews`、`positive_rate`、`steam_purchase_ratio`、`p_post`、`share_<语言>`、`playtime_median_hrs`、`playtime_mean_hrs`（评测者写评测时的游玩小时，按段加权）、`sample_n`（抽样条数，用于设定时长可靠性阈值）<br>价格：`price_at_cutoff_usd`、`price_source`、`frac_time_cut75`（深度折扣时间占比）、`avg_price_usd`（截止日前按天平均的实付价格）<br>其他：`game_age_years`、`tag_<标签>`、`charts_total_hours`（$H$） |

**result：分析结果，`viz` 只读。**

| 表 | 主键 | 字段 |
| --- | --- | --- |
| `result_estimates` | `sample_id` | `ln_a`、`ln_b`、`b_unavailable_reason`、`ln_fused`、`sigma`、`lower`、`upper`、`divergence`、`label`（高 / 中 / 低）；`calib` 样本存留一法预测，不存全量拟合后的预测；`train` 样本不写入 |

| `result_feature_importance` | `feature` | `importance`；树模型的特征重要性，供 `viz` 画图 |

### 2.3 单款查询

入口为 `python -m query <appid>`，截止日默认为当天。输入 `appid` 后依次调用 `crawler` 采集这款游戏、`pipeline` 生成一条 `query` 样本、`analysis` 用已冻结的模型和参数估算、`viz` 输出结果和查询页。查询只做预测，不重新拟合；命中排除条件（如不是游戏）时说明原因并结束；免费游戏照常估算，但只输出玩家数，不换算成销量。`query` 只负责按顺序调用，不含计算逻辑。

## 3. 数据

### 3.1 数据源

不爬取 SteamDB，其 FAQ 明确禁止爬取。

| 数据 | 来源 | 用途 |
| --- | --- | --- |
| 商店信息 | Steam `IStoreBrowseService/GetItems` 接口（一次可查多款；只能取当前价格）；标签名来自 `IStoreService/GetTagList` | 是不是游戏、标签、发售日、是否免费、当前原价 |
| 评测计数 | Steam `GetAppReviews` 接口的汇总数 | 截止日前的评测总数、好评、Steam 内购买、政策后、各语言，均为精确值 |
| 评测抽样 | Steam `GetAppReviews` 接口：截止日前按时间分 5 段，每段取该段最新的至多 100 条 | 评测者时长中位数，供信号 A 的特征和信号 B |
| 月度在线人数 | SteamCharts | 信号 B |
| 历史价格 | IsThereAnyDeal（ITAD）接口的价格变动记录，只取 Steam 商店、美国区；重新采集，不沿用早期探索版本的价格表 | 截止日原价、截止日是否免费、深度折扣占比、平均实付价格等价格特征 |
| 训练真值 | Ars Technica 2018-07-01 玩家数表 | 训练集 |
| 近年真值 | 已人工核对的近年真值表，每款一条 | 校准/测试集 |

### 3.2 采集

- 按站点限速；请求设超时，遇到限流或服务器错误时退避重试。
- 采集结果直接写入 `raw_*` 表，中断后重跑同一命令即可从断点继续，已有数据不重复请求。
- 评测计数请求量大（每款 15 次），可以几路同时发请求：`python -m crawler.sources.review_counts --workers 路数`。发请求由线程池做，写库只由主线程做；限速对所有线程合计。
- 商店信息用批量接口采集：一次请求查 200 款（实测 400 款会被拒绝），全部一万三千多款约 70 次请求。原先用的 `appdetails` 接口一次只能查一款，且按 IP 限流（实测约每 5 分钟 200 次），全量要 5 个多小时，已停用。
- 已从商店下架的游戏，评测接口返回为空，在 `raw_crawl_log` 记“未收录”，不写数据行，重跑时不再请求。
- 评测只取两类数据：限定在截止日前的计数（汇总数，不翻页），以及少量抽样评测。
- 评测抽样按时间分层：从上架时刻到截止日平均切成 5 段，每段请求一次，拿回这一段的评测总数和最新的至多 100 条（一页的上限），每款 5 次请求。第一段的起点用 1，抢先体验期间等早于上架时刻的评测也算进去；上架时刻取 `raw_store_items.release_ts`，缺失、晚于截止日或早于评测系统上线（2013-10-01）时从 2013-10-01 算起。相邻两段首尾不重叠。接口只能按时间、有帮助程度排序，做不到真随机；只取截止日前最新的 100 条会只看到截止日前不久的评测者，老游戏偏差很大（实测见 devlog 2026-11-13）。
- 抽样评测里的 `playtime_forever` 是采集当天的总时长，包含截止日之后的游玩，不用于任何计算。
- 在线人数只用截止日所在月之前的整月。
- 历史价格来自 ITAD，需要 API 密钥，放在本地 `.env` 里，不进仓库。接口默认只返回最近 3 个月，请求时要显式给一个足够早的起始时间。ITAD 不认 Steam 的 appid，先批量换成 ITAD 编号（一次 200 款），再逐款查历史。限额为 5 分钟 1000 次。

已知偏差：已删除的评测和被封账号的评测在接口中已不存在，重建出的历史评测数偏少，对 2018 训练集影响更大。2013 年前上架的游戏，评测系统上线前的玩家没有评测，分段抽样也代表不了他们；评测系统刚上线时来写评测的多是玩了多年的老玩家，时长偏长。

### 3.3 清洗与训练集门槛

- 只按输入侧条件筛选，不按 $k$ 或真值筛选。排除非游戏、零评测、重复、上架晚于截止日的样本。免费游戏保留，用“截止日原价为 0”表示，不另设免费标签。
- 是否免费按截止日当时判断：历史价格里有截止日的价格时，原价为 0 即免费；查不到时退回用商店信息里当前的 `is_free`。
- 抢先体验游戏用第一条评测的日期作为上架日。
- 商店信息是采集当天的状态。会随时间变的内容不能当作截止日的情况，要换用带时间的来源：是否免费看历史价格，是否在抢先体验看发行日与评测日期。因此标签里的 `Early Access`、`Free to Play` 这类状态词在清洗时去掉。
- 游戏的分类用标签，不用开发商填的类型（genres）。标签由开发商先设、玩家投票修正，Steam 自己的推荐和“类似游戏”也按排名前 20 的标签计算；类型只有十来种，区分度低。标签的权重是采集当天的数，会随时间增长，只用来排序和取前几个，数值本身不作特征。
- 清洗结果只保留能用的行：没有发行日的游戏不写入 `cleaned_games`，记日志。
- 评测计数清洗只排除评测数为 0 的游戏：截止日前一条评测都没有，$k$ 无从算起。评测数门槛（如不足 10 条）会随交叉验证调整，不放在清洗表，放在建样本表时。
- 近年真值表人工筛选时，只收录评测数足够、截止日不早于 Steam 评测系统上线（2013-11）的游戏；`pipeline` 再校验一次，不符合的剔除并写日志。
- 历史价格缺失的游戏不删除：用当前原价兜底，深度折扣占比和平均实付价格留空，并标明价格来源。
- 同一时刻有两条原价不同记录的游戏（ITAD 同时跟踪两个购买项或偶尔插进别的购买项），`cleaned_prices` 两条都留，建样本表时再定取哪一条。暂定取原价与前一时刻相同的那条，接不上时看后一时刻；都接不上的计数写日志。
- 有少数几组 appid 被 ITAD 归到同一个游戏编号下，查到的是同一份价格历史；建样本表时要注意它们的价格特征不是各自独立的。
- 评测者时长中位数按段加权：每段抽到的评测，每条的权重为这一段的评测总数除以这一段抽到的条数，再取加权中位数。抽到的评测里缺 `playtime_at_review` 的不计入。
- 价格特征只从第一条价格记录算起，之前的价格未知，不假设为原价。持续过久的折扣多半是漏记了“恢复原价”，建样本表时截断，阈值是可调参数（暂定 30 天，实测 99% 的折扣不超过 28 天）；`cleaned_prices` 只存实际持续天数，不截断。

训练集的评测数门槛（暂定，供参考，具体做法到建样本表时再定）：评测 1 到 9 条的游戏不进训练，因为评测数是整数，多一条评测 $k$ 就大幅变化，属于模型学不了的噪声。更高的门槛不预先设定，到训练时用几个候选值做交叉验证比较。原先“评测数 $\ge 500$”的设定不再作为默认，它的依据之一“真值抽样截掉了小游戏”与 Ars 表的实际情况不符（见 devlog 2026-11-11）。评测少的游戏仍按原思路处理：校准中加入 $\ln R$ 项，评估时大小游戏分开报告，在置信标签中降档（置信标签一节的 500 暂时沿用）。

## 4. 方法

### 4.1 信号 A：评测倍数模型

信号 A 基于“评测数 $\times k$”估算销量，分为树模型训练与线性校准两步。

第一步，在训练集上用树模型学习对数倍数 $\ln k$。模型输入为全部特征：截止日原价、好评率、标签、游戏年龄、Steam 内购买占比、各语言评测占比、深度折扣占比、平均实付价格、评测者时长中位数的对数等。政策后评测占比在训练集上恒为 0，不作为树模型的输入，只用于第二步校准。模型和特征只在这一步选择，用五折交叉验证。特征重要性也在这一步输出。

第二步，训练真值是玩家数，与销量口径不同，因此在校准/测试集上（按游戏留一法）对树模型输出做少变量线性校准：

$$
\ln k_{\text{true}} = \beta \cdot \ln k_{\text{tree}}(x) + \gamma_0 + \delta \cdot p_{\text{post}} + \eta \cdot \ln R
$$

其中 $\ln k_{\text{tree}}(x)$ 为树模型输出，$p_{\text{post}}$ 为评测政策变化后的评测占比，$R$ 为评测数；$\beta$、$\gamma_0$、$\delta$、$\eta$ 依次为缩放、截距、政策项、评测数项系数，各项含义见 [DERIVATIONS.md](DERIVATIONS.md)“校准公式”一节。

校准只用这 4 个系数，不加其他特征的修正项。原因是校准样本只有一百多条，多加特征会过拟合，也会和树模型已学到的特征作用互相抵消。训练集的截止日都在政策变化之前（$p_{\text{post}} = 0$），树模型学不到政策的影响，所以政策项必须放在校准里。

评测政策变化日期固定为 2019-11-01。依据是早期探索版本对 40 款老游戏月度评测量的实测：评测指数中位数在 2019-11 由约 0.95 跳到约 3.3，此后持续保持。

校准后，信号 A 的销量估计值为 $\hat{S}_A = R \cdot e^{\ln k_{\text{true}}}$。

### 4.2 信号 B：在线人数模型

信号 B 来自早期探索版本，利用总游玩小时除以人均游玩小时估算销量。

第一步，计算累加到截止日所在月前一个月的总游玩小时 $H$：

$$
H = \sum_{m} c_m \cdot d_m
$$

其中 $H$ 为总游玩小时，$m$ 为统计月份（累加到截止日所在月的前一个月），$c_m$ 为第 $m$ 个月的月均在线人数，$d_m$ 为第 $m$ 个月的当月小时数（上架当月只按上架后的天数计算）。

第二步，根据评测者时长中位数计算人均游玩小时 $h$：

$$
\ln h = a + b \cdot \ln t_{\text{med}}
$$

其中 $h$ 为人均游玩小时，$t_{\text{med}}$ 为抽样评测的 `playtime_at_review` 中位数，$a$ 和 $b$ 为回归参数。参数 $a$、$b$ 在训练集上拟合（目标为总小时除以真实玩家数），另做五折交叉验证。评测时长偏低（玩家写完评测后继续游玩）的平均影响由这一步拟合吸收。不用 `playtime_forever`：它包含截止日之后的游玩，而 $H$ 只累加到截止日，两者口径不一致。

第三步，计算信号 B 的输出 $\hat{S}_B$：

$$
\hat{S}_B = \frac{H}{h}
$$

其中 $\hat{S}_B$ 为信号 B 的销量估计值。三步公式的来源见 [DERIVATIONS.md](DERIVATIONS.md)“信号 B”一节。

只有在线人数从上架初期就有记录、且截止日前已积累足够记录时才计算 B，否则只用 A；具体条件在代码中设定。累计漏掉上架初期会严重低估 $H$。信号 B 的覆盖率有限，早期探索版本约一半真值可用，销量低于 1 万的游戏几乎不可用。

### 4.3 信号融合

每路信号 $i \in \{A, B\}$ 的误差 $\sigma_i$ 取该路留一法对数残差的标准差，是一个固定值，不随单款游戏变化。在对数空间按固定权重 $w_i = 1/\sigma_i^2$ 加权融合：

$$
\ln \hat{S} = \frac{w_A \ln \hat{S}_A + w_B (\ln \hat{S}_B + \mu_B)}{w_A + w_B}
$$

其中 $\ln \hat{S}$ 为融合后的对数销量估计值，$w_A$、$w_B$ 分别为信号 A 和信号 B 的权重，$\mu_B$ 为信号 B 的残差均值修正项。信号 A 已经校准，不加修正项，所以只有 A 时结果等于 A；信号 B 没有在真值上校准，要加 $\mu_B$。缺少的信号不参与计算，融合结果总在可用信号之间。

$\sigma_A$、$\sigma_B$、$\mu_B$ 都在留一法中计算：预测某款游戏时，只用其余游戏的残差。

预测区间使用的 $\sigma$ 同样取固定值：两路都可用的样本取融合结果留一法残差的标准差，只有 A 的样本取 $\sigma_A$。两路共享评测者时长、误差不独立，直接取融合结果的残差就不必单独估计两路的相关程度。区间的实际覆盖率在评估中检验，不足时整体放宽。推导见 [DERIVATIONS.md](DERIVATIONS.md)“融合”一节。

### 4.4 置信标签

权重无法反映单款游戏上某一路信号是否离谱，因此由置信标签提示分歧。两路信号的分歧 $D$ 定义为：

$$
D = \left| \ln \hat{S}_A - (\ln \hat{S}_B + \mu_B) \right|
$$

分歧阈值取固定值 $\tau = 0.5$，即两路估计相差约 1.65 倍。该值在看到留一法结果之前确定，之后不按结果调整。

| 信号 B 可用性 | 分歧程度 | 评测数条件 | 置信标签 |
| --- | --- | --- | --- |
| 有 B | 分歧小（$D \le \tau$） | 评测 $\ge 500$ | 高 |
| 有 B | 分歧小（$D \le \tau$） | 评测 $< 500$ | 中 |
| 有 B | 分歧大（$D > \tau$） | 不限 | 低 |
| 无 B | 不涉及 | 评测 $\ge 500$ | 中 |
| 无 B | 不涉及 | 评测 $< 500$ | 低（外推） |

两路分歧大时，融合的命中率可能低于单路，但事先无法判断该信哪一路，因此不改融合公式，由“低”标签提示，原因见 [DERIVATIONS.md](DERIVATIONS.md)“估计值在中间，命中率不一定在中间”一节。作为参考，早期探索版本中分歧最大的 $1/4$ 样本命中率约 29%，其余约 59%。

## 5. 评估与测试

### 5.1 评估方法

对校准/测试集中的每一款游戏做留一法：把它拿出来，用其余游戏拟合校准系数、$\sigma_A$、$\sigma_B$ 和 $\mu_B$，然后分别预测信号 A、信号 B 和融合结果，把这三个预测与真值比较。被测游戏不能出现在任何拟合数据里。留一法只用来评估，产出的是一组成绩，不产出最终使用的参数。

### 5.2 最终模型

评估完成后，用全部数据重新拟合一次，得到交付使用的最终模型，称为全量拟合：

- 树模型与信号 B 的 $a$、$b$：用全部训练集拟合。超参数和特征沿用五折交叉验证选定的结果，不再调整。
- 校准系数 $\beta$、$\gamma_0$、$\delta$、$\eta$：用全部校准/测试集拟合。
- $\mu_B$、$\sigma_A$、$\sigma_B$ 和融合区间的 $\sigma$：取全部校准/测试集上的留一法残差计算。

全量拟合的结果保存后即冻结：单款查询和展示都只读这份结果，不再拟合。报告中的准确度一律引用留一法的成绩，而不是全量拟合后在同一批数据上的成绩，因为后者用到了被测游戏本身，会偏乐观。

### 5.3 比较指标

- 主指标：$\pm 30\%$ 命中率，按信号 A、信号 B、融合分别报告，并按销量档和置信标签分组报告。
- 辅助指标：95% 区间的实际覆盖率。
- 命中率和覆盖率都是比例，95% 置信区间用 Wilson 区间公式直接计算，推导见 [DERIVATIONS.md](DERIVATIONS.md)“比例的置信区间”一节。

### 5.4 测试

自动化测试只检查一件事：数据不能泄露。包括：特征的时间不晚于截止日；`playtime_forever` 不进入任何特征；训练集不含校准/测试集的 `appid`；被测游戏不参与自己的预测；单款查询不改变已拟合的模型和参数。

### 7.2 候选改进

主线跑通后再考虑，按需取用。先只用主线特征得到基线，之后每次只试一项并与基线对照。加特征遵守三条：说得出它为什么会改变 $k$；同一件事只留一个代表；交叉验证没有明显改善就不留。

| 方向 | 说明 |
| --- | --- |
| 耐玩度 | 抽样评测时长的均值与中位数之比，加入信号 B 的人均时长拟合。早期探索版本数据上能减小 B 的误差，但没有提高命中率 |
| 评测时间线 | 首月评测占比、评测数的衰减速度等特征 |
| 更多价格特征 | 由同一份价格历史再算：任意折扣的时间占比、最大折扣、每年打折次数、永久降价幅度等；先在 `pipeline` 里算出来，留不留由交叉验证决定 |
| 慈善包与免费赠送 | ITAD 另有慈善包和免费赠送记录（带起止时间），这类拥有者很少写评测，可能抬高 $k$；需新增两张 raw 表，老记录是否齐全尚未核实。与 Steam 内购买占比有重叠；慈善包要区分主打与陪衬（可用所在档位价格等间接指标），先试慈善包 |
| 区域定价 | 加采中国区等价格，用相对美国区的比值作特征；初步比较显示各区折扣基本同步，差别主要在原价水平 |
| 标签权重 | 原始表里有每个标签的权重，可能反映标签有多贴切。数值含义不明（与玩家数取对数后的相关系数约 −0.2，不像投票人数），主线只用它排序；要试时从 `raw_store_tags` 取，不进清洗表 |
| 分语言好评率 | 不同语言的玩家评价习惯可能不同。但除英语外，各语言评测数的中位数只有 0 到 3 条，好评率多半是噪声或算不出；要试时从 `raw_review_counts` 取 |
| 第三路信号 | 关注者数、成就解锁率等，可在两路分歧大时帮助判断该信哪一路 |
| 真值增多后 | 小游戏单独修正、按开发商分组交叉验证、纳入评测少于 500 的游戏等 |
